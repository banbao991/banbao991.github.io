# 苔谷农场 · 设计与协作约定

苔谷农场是一座会自行运转、也允许玩家轻轻介入的像素小世界。直接打开 [index.html](index.html) 可以游玩。

当前正式版本为 **v1.2**（2026-10-09），见 [v1.2 版本说明](logs/v1.2.md)。包含 [v1.1 开发成果](logs/v1.1.md) 与后续村庄建设、草地养护和修复；首个正式版本为 [v1.0](logs/v1.0.md)。侧栏提供加载 v1.2 默认农场，存档位于 `saves/v1.2/`；原 `saves/v1.0/` 保留，已有玩家进度仍按原保存状态继续。

世界设定、具体数值和操作说明见 [世界与玩法](doc/世界与玩法.md)；文件职责与加载方式见 [代码结构](doc/代码结构.md)；启动、演变、绘制和存档的完整流程见 [运行逻辑](doc/运行逻辑.md)；场景层级约定见 [渲染与遮挡](doc/渲染与遮挡.md)；玩家文字遵守 [界面文案](doc/界面文案.md)。商人、消费与生活互动见 [城镇发展](doc/城镇发展.md)，施工队、居民迁入和草地养护见 [村庄发展](doc/村庄发展.md)，实现证据见 [持续开发记录](doc/持续开发记录.md)。新增玩法时，同步更新对应文档，README 只保留设计方向和协作约定。

## 设计理念

- **温暖且有生活感。** 以暖色调、清晰的像素轮廓和可读的场景层次呈现田地、牧场、森林与村庄。装饰应帮助辨认地点、季节和活动，避免把画面堆得过密。
- **世界自己生活。** 工人、家畜、野生动物、作物与天气都应遵循能解释的规则。玩家不操作时，农场仍能工作、休息、觅食、成长和建设；玩家点击后，应能看到明确而局部的回应。
- **变化有过程。** 昼夜、季节、天气、植物生长和建筑开放应有视觉过渡。即使夜间时间加速，也要看见天色变暗再变亮；避免跨日或达到门槛时突然换掉整幅画面。暂停时世界时间和角色路线冻结，角色仍可眨眼、摆尾或做其他原地小动作；云影、雨丝和雪花继续移动，天气类型与过渡进度保持不变。
- **复杂度来自交互。** 新元素优先与已有系统形成关系，例如采集物影响动物、订单改变种植选择、天气改变工作和栖息。每个可采集、可垂钓或可收获的对象都应有独立状态和反馈。
- **地图是一张连续的世界。** 扩建须尊重河道、桥、道路、建筑、田地和活动路线；留出草地缓冲与适当空白。主地图、小地图、悬停提示、点击命中和完整地图导出应指向同一套世界坐标。
- **公共空间有固定的生活节奏。** 苔谷广场位于河西的交通中心，木台、水井和座椅提供日常可辨认的空间。广场建成后，每逢第十天全体村民在此欢庆，按清晨金币筹备并保留经营储备；活动设施要留出通道，居民移动要有目的、人数上限和停留过程；新增居民时要接入聚会路线、停工、返家、悬停反馈与完整存档。阿运出发前要检查次日是否为欢庆日，避免把两天行程排进活动日。
- **视角自由，进度可靠。** 地图可以拖动、缩放、进入纯享视图；当前世界应在刷新后延续，并能完整导入导出。图片导出应覆盖整张地图及导出时的状态。

## 给后续 Agent 的要求

1. 先读本文件、[世界与玩法](doc/世界与玩法.md) 和 [代码结构](doc/代码结构.md)，再定位相关模块。现有世界规则是修改的起点；如果玩法改变，更新文档中的对应描述与数值。
2. 新增区域或对象时，同时设计它的可见形态、时间或天气行为、交互反馈、悬停提示、小地图表现、绘制层级以及存档状态。没有交互的装饰也要检查遮挡与密度。
3. 共用世界坐标定义，检查对象与河湖、道路、建筑、田地及彼此的重叠。新田地与道路之间至少保留一格草地。检查缩放、拖动、纯享模式以及完整地图导出中的位置一致性。玩家指出的空地可能是尚未发展的设施预留地，先检查所有建设完成后的布局；成熟阶段已有用途或过于拥挤时，暂不填充。扩建花园等已有区域时优先沿用其发展规则，收藏架随真正购得的新收藏出现，不预先堆放空架。
4. 新增物体必须先确定地表、落地实体、附着物或飞行层，再接入统一绘制队列；具体约定见 [渲染与遮挡](doc/渲染与遮挡.md)。实体按未受跳跃、摆动影响的接地点排序；人物按脚底，建筑按底边，树按树根。围栏和桥必须拆开地面、后侧与前侧；彩带跟随支撑木柱，停栖鸟跟随承载物。不要把整片区域、休息人物或夜间实体灯光直接补画到最前面。修改后检查所有居民和动物从后方走到前方、暂停、欢庆、夜间与全图导出，并同步检查命中区域。
5. 保持 `css/`、`js/` 按功能拆分；新增大功能使用独立模块，遵守页面脚本的加载顺序与本地 `file://` 可运行的方式。若确实引入第三方库，将文件放在站点根目录的 `libs/`，不要依赖运行时联网。 角色状态与平日行为放在 `life/`，共用欢庆规则放在 `festival-life.js`；`art/` 只绘制，界面刷新与演变调度分开。首页是脚本清单的唯一来源，`ui/app.js` 最后启动，响应式样式最后加载。
6. 保留浏览器自动存档与 JSON 完整状态的语义。新增会持续变化的对象时，把其必要状态纳入保存、导入校验和恢复；不要只保存日期、金币或静态解锁。

7. 面向玩家的文字只写场景、当前状态、玩法条件与操作反馈。布局需求、实现过程和修改历史放在注释或文档，避免混入悬停提示、商品说明和日记；具体示例见 [界面文案](doc/界面文案.md)。

## 修改工作流

v1.2 已整理为正式发布版本，本轮功能、修复与验证完成。[村庄发展](doc/村庄发展.md) 记录实际价格、工期、居民名单和养护规则，默认选择与实际验证保留在对应开发历史。发布版本号与存档格式号分别管理；后续开发以 v1.2 为基线并另建历史文件。

1. 明确改动涉及的世界规则、坐标、绘制、交互和存档模块；先核对现有实现，再动手。
2. 实现后检查日夜与天气过渡、不同缩放级别、区域悬停提示、对象点击、移动路径和遮挡。对新区域还要检查小地图与全图导出。
3. 运行 `node kits/farm/tests/smoke.cjs`；必要时对修改的脚本运行 `node --check`。测试通过后同步更新 `doc/`，并在交付时说明实际验证过的范围。
4. 可选设计问题若用户长时间未回复，采用符合现有规则的默认方案，并在 [记录索引](doc/持续开发记录.md) 指向的当前文件写明选择与原因。每项功能的过程和实际证据写入该文件，版本日志汇总相对于开发基线的最终变化。已有授权内的工作继续推进；需要明确授权的操作仍须等待确认。当前开发仅限本地，不发布、部署、提交或推送。
