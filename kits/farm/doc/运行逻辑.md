# 苔谷农场：代码运行逻辑

[设计与协作约定](../README.md) · [世界与玩法](世界与玩法.md) · [代码结构](代码结构.md)

本文按实际执行过程解释农场如何启动、演变、绘制和保存。各文件的职责清单见「代码结构」，玩法数值与操作说明见「世界与玩法」。以下以当前实现为准。

## v1.2 建设系统接入

完工后的养护也由 `updateVillageDevelopment(dt)` 调度：先推进慢速杂草生长，再检查自动委托；十二项工程与迁入全部结束后，同一对工人进入养护分支。生长用保存的半秒累计时钟、连续季节/天气权重、再生等待和随机种子；委托保存付款、三十簇目标进度和每名工人的认领/动作。每帧不重新生成草地，截图、卡片和小地图只读取。新状态在 `farm.development.maintenance`，旧缓存和导入统一补齐；暂停退出调度，显式点击委托只安排任务与付款。完整规则见 [村庄发展 · 完工后的养护](村庄发展.md#14-完工后的草地养护)。

1. `state.js` 的新农场创建自然阶段的 `farm.development`。读取旧缓存时，`parseFarmSave` 先校验原状态，再调用 `save-migrations.js` 补齐已存在的设施，校验建设字段后才替换世界。文件导入、ZIP 解码后和默认存档都走同一入口。
2. 原 `expandIfReady()` 仅推进五项村民自主发展：东侧田地、蜂箱、主场南扩、下方田地和集市。温室、羊舍、山羊舍不再由总体等级瞬间出现。主场南扩带来阿麦；未开放牧场的南田货物存到主场货箱。
3. `updateActors()` 首先检查暂停，随后调度 `updateVillageDevelopment(dt)`。工程达标时记录登记序号并追加到 `farm.development.queue`；实际开工读取这个数组的当前顺序。玩家点击等待项时，`villageQueuePriorityIndex()` 检查连续前置关系，`prioritizeVillageProject()` 只移动该项，其他项相对顺序和正在施工的工程不变。暂停时也允许这项玩家安排，界面立即保存并保留按钮焦点；它不推进模拟或扣费。队首前置已完成、资金足够、保留储备且白天非欢庆时开工，费用只扣一次。前一户实际安顿后才能接下一项。
4. 工人使用只包含已通行路段的道路图。路段约 32 像素，逐段计时铺设；桥面可显示部分施工，但整座接通前不加入通行图。共用路段具有唯一 ID。道路完成后进入清理、设施建造和收尾；进度取决于实际到达工地的工作时长，夜晚、欢庆停止，雨雪减速或停工。

   初始开放按路段归属决定：河西靠河纵路归森林/广场，广场两条入口归广场，中央桥东侧超过阿运停靠连接的尾段归矿区；仍保留原 ID 和几何。主地图、小地图、通行与建设复用读取同一 `villageRoadGraph()`，已完全覆盖的共用路面不重复施工。

   湿地木板桥的铺板保留在道路记录和绘制中，但不参与村庄道路行程的最近入口选择；该小桥通过东岸草地短距接近，与村路没有直接相连。`villageActorMove()` 发现当前目标未到达且路线为空时重新规划，包括恢复旧存档中已经缓存的失败路线；到达目标后清空路线并原地休息，不再次绕回道路中心。
5. 屋主开工后加入协助演员，生产尚未开放。施工末段共用「工程收尾」名称；完工后才转入 `moving`，沿真实路线到住处后恢复原人物的生产模块。山羊牧场配置 `ownerReturnsHome`，通过 `villageResidentReturnsHome()` 区分阿牧返回已有住宅与新屋主迁入：侧栏、人物活动、行李和到家日记使用同一判断。保留原 `moving` 存档阶段和走路流程，不增加持久字段。施工队和新屋主夜里回住处，欢庆使用共享活动引擎，暂停只保留绘制中的原地动作。
6. `villageSiteOpen` / `villageResidentWorking` 同时控制生产、采收、收货、设施绘制与悬停。阿运只根据返程出发时已开放货箱的现货计划路线；阿棠的来访、备货、营业与小工程都需要驿屋已完工，来访仍要求至少 5000 金。旧存档已付费的小工程保留进度。
7. 绘制函数读取工程状态，不推进工作或扣钱。自然植物按实际设施占地逐渐清除，外围保留；房屋、栈桥、围栏和轨道有分阶段形态，工人、材料和建筑进入同一深度队列。小地图、鼠标与全图导出读取相同坐标。

   村口右侧收矿摊屋列入 `VILLAGE_FACILITIES.mine`，随矿区搭建设施阶段显示框架、墙体和屋顶；完工后 `villageMarketStallOpen(1)` 同步开放摊屋、矿箱、院落地面、小地图和收矿提示。左侧农产摊继续读取自主开市条件。外部配套施工占地也能显示对应工程提示。
8. `farmExportText()` 和自动存档包含完整 `farm.development`：登记序号与当前施工队列、付款、路段、分段计时、阶段工作量、临时居民、施工演员路线及欢庆进度。导入允许玩家调整后的队列顺序，但仍校验登记序号唯一、状态一致及未完成前置必须已开工或位于队列前方，不再要求队列按历史序号递增。原 `runtime` 保存已入住角色原有工作与位置；恢复两者后原循环继续。不能按日期或金币推算完工。

侧栏居民展示由 `ui/development/resident-roster.js` 保留稳定按钮，详情读取同一个角色的实时状态。`tick()` 在暂停判断之外调用小像更新，按显示时钟限为每秒 12 帧；各小像使用独立 Canvas，不调用人物行为、不切换主地图上下文、不增加存档字段。「旅人与小镇」的显示条件是已有 `farm.town.visits > 0`，所以首次来访后离开也保留记录入口。

详细数值和道路/迁入规则见 [村庄发展](村庄发展.md)，实际测试见 [当前记录](history/持续开发记录-v1.1.md)。下面原有系统的细节中，偏远设施的行为均以对应工程开放为前提。

## 1. 先看整体

农场运行在浏览器中。HTML 提供画布、按钮和右侧卡片，CSS 负责页面布局，JavaScript 维护世界状态并用 Canvas 绘制像素场景。世界演变不需要后端服务；本地 HTTP 服务主要负责提供页面和 Markdown 阅读工具。

```text
index.html 按顺序加载脚本
  └─ 创建或读取 farm，初始化人物和动物
      └─ ui/app.js 恢复动态状态，启动 tick()
          ├─ 推进日期、工作、移动、采集、货运
          ├─ 更新右侧卡片、小地图和悬停文字
          ├─ render() 绘制当前世界
          └─ 保存 farm + runtime，安排下一帧

鼠标 / 键盘 → 输入处理 → 修改同一份状态 → 后续帧显示结果
导入存档    → 校验 → 替换同一份状态 → 原来的循环继续运行
```

代码使用普通的 `defer` 脚本，没有构建步骤，也没有 ES 模块的 `import/export`。各文件共享页面中的变量和函数；`core/`、`life/`、`art/`、`ui/` 表达职责边界，并不提供独立的模块作用域。

## 2. 页面启动时发生什么

入口是 [index.html](../index.html)，最终启动代码在 [ui/app.js](../js/ui/app.js)。

| 顺序 | 加载或执行内容 | 目的 |
| --- | --- | --- |
| 1 | 本地 `fflate`、共享地图坐标、工具函数、配置、DOM 辅助 | 提供后续模块需要的基础定义 |
| 2 | 存档解析、ZIP 编解码、经济与欢庆预算函数 | 让初始状态可以创建或读取 |
| 3 | `state.js` 执行 `let farm = loadFarm()` | 有有效缓存就读档，否则创建新农场 |
| 4 | 日历、欢庆及各个 `life/` 文件 | 定义行为，创建居民、动物，初始化必要资源 |
| 5 | 演变调度、运行状态快照、绘制与 UI 文件 | 准备更新、恢复、绘制和操作入口，绑定事件 |
| 6 | `app.js` 执行启动部分 | 恢复动态快照、准备欢庆、刷新界面、启动动画循环 |

**恢复分成两步。** `loadFarm()` 先解析世界数据，把人物等动态数据暂存到 `loadedRuntime`。等所有角色与校验函数都定义好，`app.js` 再调用 `restoreRuntimeSnapshot()` 恢复位置、工作进度和路线。这样读取缓存时不会提前调用尚未加载的行为模块。

启动部分随后调用 `prepareFestival()`、`syncToolUI()`、`updateUI()`，最后通过 `requestAnimationFrame(tick)` 开始运行。若当前是欢庆日，会保存已经筹备过的状态。

加载顺序有实际约束：可以在函数体中引用稍后定义的函数，但不能在文件顶层执行时调用还没有加载的函数。新增文件需要同步加入首页脚本清单；新增全局名称也需要避免冲突。

## 3. 世界状态放在哪里

### 3.1 三类数据

| 类别 | 典型内容 | 所在位置 / 保存方式 |
| --- | --- | --- |
| 世界数据 | 日期、日内时间、天气、金币、田地、建设、订单、货箱、苗圃、菜圃、矿产、欢庆支出 | 主要在 `farm`，作为存档的 `state` 保存 |
| 动态运行数据 | 人物和动物位置、移动目标、当前任务、行动进度、货车货物、路线下标、欢庆活动、动画时钟 | 各行为文件中的角色对象，由 `captureRuntimeState()` 汇总为 `runtime` |
| 临时显示数据 | DOM 引用、鼠标位置、当前提示、拖动过程、当前画布尺寸、绘制缓存 | 留在 UI 或绘制模块，需要时重建 |

`farm.view` 的视角和缩放、`farm.paused`、账本展开偏好、纯享提示偏好也会保存。实际浏览器全屏状态和当前鼠标悬停对象不作为存档恢复。

共享地图坐标来自 [core/world-layout.js](../js/core/world-layout.js)，世界尺寸、时间与作物规则来自 [core/config.js](../js/core/config.js)。它们是代码配置，不是每个存档都复制一遍的世界数据。绘制、道路路线、命中和小地图应尽量复用这套定义。

### 3.2 为什么不能只保存 `farm`

例如阿运正在返程：货箱库存属于 `farm.depots`，已经装上车的货物属于 `courier.cargo`，当前路段和夜间休息路径属于 `courier`。只保存库存和日期，会丢失车上的货物或正在执行的路线。

类似地，阿芽的苗床成熟时间属于 `farm.nursery`，她正在走向哪畦、采到什么进度属于 `nurseryKeeper`。完整存档同时保存两部分，才能从保存的位置继续。

## 4. 每一帧怎样推进

[ui/app.js](../js/ui/app.js) 的 `tick(stamp)` 是唯一的主循环。浏览器每次安排一帧时调用它，角色没有各自独立运行的定时器。

下面保留实际的调用顺序，省略日志和界面细节：

```js
dt = Math.max(0, Math.min(0.065, (stamp - last) / 1000));
last = Math.max(last, stamp);
now += dt;

if (!farm.paused) {
  motionNow += dt;
  nightRate = farm.phase >= NIGHT_START ? 2.1 : 1;
  farm.phase += dt * farm.speed * nightRate / DAY_SECONDS;
  if (farm.phase >= 1) nextDay();
  updateActors(dt * farm.speed * nightRate);
  // 约每 4 秒自动保存，约每 200 毫秒刷新界面
}

updateMapHover(dt);
render();
requestAnimationFrame(tick);
```

确认框关闭、重启或导入后，浏览器可能交付早已排队的旧帧。`dt` 不能小于零，`last` 也不能退回旧时间；待新帧超过当前基准后才正常推进，避免日期、角色路线和存档倒退。重启通过 `createFarmWorkers()` 重建初始工人，清除旧任务、欢庆路线、招手和行走进度；完整导入随后用存档中的 runtime 恢复真实动作。

### 4.1 三种时间的区别

| 时间 | 推进方式 | 用途 | 暂停时 |
| --- | --- | --- | --- |
| `now` | 每帧累加 `dt` | 雨雪粒子、云影、眨眼、挥手等显示动作 | 继续 |
| `motionNow` | 未暂停时累加原始 `dt` | 河流水纹、部分动物的位置曲线、生态互动期限 | 停止 |
| `farm.day + farm.phase` | 日内时间按速度与夜间倍率推进，跨日增加日期 | 日程、季节、成熟与再生时间 | 停止 |

角色更新收到的 `dt` 也乘以速度和夜间倍率，所以加速会同时加快通勤与工作。`now`、`motionNow` 没有乘这些倍率，因此视觉粒子与部分环境运动不随时间按钮同比加速。

一天从 06:00 到次日 06:00，`phase` 从 0 走向 1；`NIGHT_START = 14 / 24` 对应 20:00。基础参数 `DAY_SECONDS = 72`，但夜间使用 2.1 倍速，所以 1 倍速度下一整天约 56 秒。夜晚仍逐帧变暗、返家、再变亮，并没有直接跳过。

`dt` 上限为 65 毫秒。页面在后台被浏览器停止或降低帧率时，不会按真实经过的全部时间追赶；关闭页面期间也没有离线收益结算。

### 4.2 暂停的边界

暂停会停下日期推进、角色移动、工作进度、成熟进度和循环中的定期保存。画布仍绘制，悬停仍刷新，天气粒子和原地小动作继续播放；季节与天气的过渡进度保持不变。

输入事件仍然可用：拖动、缩放、导出，以及手动播种、浇水、采集等操作可以照常处理。它们修改状态后，相关事件仍可以调用 `save()`。因此「暂停演变」冻结的是自动推进，并不是给所有数据加上只读限制。

## 5. 跨日更新与渐变

[core/calendar.js](../js/core/calendar.js) 的 `nextDay()` 是每日结算入口，顺序如下：

1. 保留上一日天气和生长季节，增加日期，将 `phase` 设为 0。
2. 若是欢庆日，筹备预算，并将仍有效的订单截止日顺延一天。
3. 清空当日集市展示、重置每日产量和挤奶状态，按周期补充鸡蛋、水果、蜂蜜、羊毛和山羊奶的可收取标记。
4. 保存 `weatherFrom`，抽取新天气；冬季有 32% 概率下雪。
5. 处理菜圃每日消耗与节日分享，生成当日林间采集物和湖中鱼点。
6. 结算主场作物的生长，考虑浇水、冬季、温室和当天实际播种时间；按新天气更新浇水标记。
7. 重置牛奶与农务伙伴任务，删除过期订单并补充新委托。
8. 记录日记，检查建设解锁，刷新界面并保存。

**各类植物并不共用一种成熟模型。** 主场作物的 `age` 在跨日时结算；`cropVisualProgress()` 会加入当天已过去时间，显示连续生长的外观，但农务收获任务仍以结算后的 `age` 判断。香草、苗床和矿脉则记录采收时间或 `readyAt`，用 `day + phase` 判断进度和再生。

季节的规则名称每 8 天切换一次，视觉颜色通过 `seasonTransition()` 在季节边界前后各 1.5 天内混合。天气保存前后两种类型，`weatherVisual()` 在新一天前 15% 时间内平滑改变云量、雨量与雪量。规则状态与显示过渡分别计算，画面不必在日期变化那一帧整体换色。

## 6. 居民和动物怎样自己行动

### 6.1 集中调度，分别实现

[core/simulation.js](../js/core/simulation.js) 的 `updateActors(dt)` 按固定顺序调用：

```text
农场动物 → 农务伙伴 → 阿运 → 阿宁 → 阿蓼通勤 → 阿葵
→ 阿蓼垂钓 → 阿森 → 森林动物 → 西湖 → 西南小湖
→ 北岭 → 山羊 → 湿地苗圃与阿芽 → 矿区与阿矿 → 广场猫与麻雀
```

这些函数在同一个线程中顺序执行，读写同一份状态。例如农务伙伴先把货物放进箱子，随后阿运的更新就能看到它。帧内顺序可能影响「这一帧能否立即收走」，但货运整趟路线另有固定的规划时点。

并非每个可见生物都需要一个更新函数。湿地黑水鸡、蜻蜓等可根据 `motionNow`、天气和互动状态直接计算当前位置；绘制与命中调用同一个位置函数，暂停后位置曲线也就停止。

### 6.2 常见行为结构

```text
检查欢庆 / 夜晚 / 是否开放
  → 选择有效任务或日程
  → 沿路径移动
  → 到达目标后累计行动时间
  → 修改库存或资源状态
  → 寻找下一项工作；没有工作才去休息
```

| 居民 | 平日逻辑入口 | 工作怎样连接 |
| --- | --- | --- |
| 阿满、小禾、阿青、阿麦 | `updateFarmWorkers()` | 共做主场农务；按优先级和距离挑任务，排除其他伙伴已占用的任务 |
| 阿栀、阿牧 | `updateFarmWorkers()` | 分别挑香草、羊毛与山羊奶任务；空闲回各自休息点 |
| 阿芽 | `updateNurseryKeeper()` | 找最近的成熟苗床，采完直接安排下一畦；没有成熟苗床才休息 |
| 阿矿 | `updateMineLife()` | 开采、休息、取车、送矿、喝茶、返家等 `mode` 切换；采完还有矿就接着采 |
| 阿森 | `updateForestKeeper()` | 普通日清晨确定采菇或巡林；逐朵采菇至当日上限，或观察动物 |
| 阿蓼 | `updateAngler()` / `updateAnglerFishing()` | 通勤与垂钓分开；使用真实鱼点，保存当日额度、目标和钓鱼进度 |
| 阿葵 | `updateOrderKeeper()` / 菜圃任务函数 | 通勤接入角色模块，具体轮作与采收由菜圃模块处理 |
| 阿宁 | `updateVillageWalker()` | 在小屋前散步，夜间返家 |
| 阿运 | `updateCourier()` | 两日货运与夜间休息，详见下一节 |

行为通常由 `mode`、`goal`、`task`、`route`、`index`、`action` 等字段表示。到达后改变阶段，下帧继续更新；不是一次函数调用就把整个日程执行完。

路径实现按场景选择：货运和送矿采用预设道路折点，苗圃使用畦间通道，守林人和广场活动有各自的寻路规则。当前没有统一控制全世界所有角色的寻路或碰撞引擎，新增道路仍需要检查实际经过的角色路线。

广场日常动物由 `updatePlazaLife()` 调度。两只猫使用独立模式与避开家具的网格路径；麻雀保存落点编号、飞行目标与高度，猫或居民靠近时改飞高处。它们使用角色更新的时间步长，暂停不会改变路线；摆尾、眨眼等显示动作读取 `now`。猫用实际雨雪强度至少 .25 判断新外出和返屋，麻雀仍沿原雨天离开规则；欢庆只改变动物的落点偏好，不把它们加入居民聚会名额。`plazaCats`、`plazaSparrows` 一并进入运行快照。

## 7. 货物、订单、金币与建设

### 7.1 主农场经济链

```text
种植 / 挤奶 / 采集 / 垂钓
  → stockGood() 放进产地货箱 farm.depots
  → collectDepot() 转移到 courier.cargo
  → deliverCourierGoods() 在集市出售
      ├─ 增加金币与累计送货量
      ├─ 推进对应订单，完成后追加奖励
      ├─ updateNurseryMilestones() 修复更多苗床
      └─ expandIfReady() 检查下一阶段建设
```

收获和销售是两个时刻。农产品放进箱子时不会直接获得售价；送到集市才产生收入。订单进度也按送达的作物增加，同类委托优先分配给截止日更早的订单。订单优先开关通过 `chooseCrop()` 影响后续自动播种选择。

种子会扣金币；自主发展在达到余额门槛时扣对应费用，`expandIfReady()` 每次处理一个分支，可能由收获、送货、送矿或跨日触发。大型工程另由施工队按达标时间排队，队首开工时一次付费并保留经营储备，不能由总体等级替代施工进度。

### 7.2 阿运的规划时点

阿运先从村口出发去主场小屋，次日返程收货。去程不锁定采集点：从 `rest` 切换到 `return` 的那一刻，才执行：

```js
courier.plannedDepots = DEPOT_IDS.filter(id => villageDepotOpen(id) && depotCount(id) > 0);
```

本趟计划顺序为 **主场 → 西湖 → 湿地苗圃 → 牧场 → 山谷香草 → 森林**，跳过规划时没有货物的箱子。森林是否有货决定是否走森林绕行路线，否则走直接返村口路线。

规划的是「去哪些地方」，不是预定收货数量。到一个计划中的箱子时，`collectDepot()` 会取走那一刻的全部库存；规划之后才开始有货、且没列入本趟计划的箱子留待下趟。路线下标、已收货物和夜间返家路径都会保存。

### 7.3 两套独立的区域生产

- **东岸菜圃：** 蔬菜进入 `farm.eastGarden.basket`，用于村口日常消耗和节日分享，不进入阿运的货车或农场订单。菜篮只有菜圃旁的一处实体展示。
- **矿区：** 矿石进入 `farm.mine.stock`，阿矿独立装车、送到矿摊、获得金币。每四天一趟，送矿日不采矿；送达后将 `nextDeliveryDay` 设为实际送达日期加 4，再推车返回、去茶亭、回家。矿产不计入阿运的普通送货量。

苗圃修复由普通货物累计送达量推动；开放苗圃也会改善香草再生和果园产出节奏。这是生产区域间已经实现的一条反馈关系，并没有额外的种苗库存扣除流程。

## 8. 欢庆日怎样接管工作

欢庆判定在 [life/festival-life.js](../js/life/festival-life.js)：`isFestivalDay(day)` 同时要求 `day % 10 === 0`、`villageSiteOpen('plaza')`，以及广场的 `completedAt <= day`。完工时间带日内小数，因此第十天白天才完工时，当天继续工作，从下一次十日欢庆开始；旧版已经建好的广场保留欢庆。预算、订单顺延、居民与工人停工、阿运前一天停发、纸灯活动都读取这项共享判定。未建广场时，这些日子照常工作，不发生欢庆扣款。欢庆不停止整个世界：天气、植物和动物继续演变，居民的行为入口改为聚会流程。

### 8.1 清晨一次筹备

[core/festival-budget.js](../js/core/festival-budget.js) 的 `prepareFestival()` 根据清晨余额扣除预算：

```text
预算 = max(0, floor(min(清晨金币 × 1%, 清晨金币 − 300)))
```

结算保存到 `farm.celebration`，包括日期、起始余额、预算、规模、累计支出和次数。检查 `celebration.day` 可保证同一天刷新、恢复或重复调用不会再次扣款。界面和绘制只读取已筹备结果。

### 8.2 赴会、活动和返家

居民所属模块先判断欢庆日，暂停普通任务，再调用 `updateFestivalActor()`：

```text
out 沿路赴会 → gather 广场活动 → back 沿路返家 → home 在家休息
                                      次日按角色规则重新出门
```

到场后的活动交给 [life/festival-activities.js](../js/life/festival-activities.js)。居民选择取餐、聊天、观看、休息、跳舞或演奏，预留活动点，在避开家具的短路径上移动，并限制最多四人同时换位置。路线、停留时间与活动进度保存在角色的 `festival.activity` 中。

预算等级影响餐桌和节目；等级足够时，在日内 `.22` 至 `.32` 阶段安排演奏与舞会。到 `.44` 阶段开始散场，居民直接返家，不回工作岗位。次日从家里恢复自己的日程。

### 8.3 周期性工作的例外

- 阿运在村口且次日是欢庆日时，不开启新的两日货运，留在村口。欢庆当天在村口就参加；若处于主场一侧的行程状态，则在主场休息。
- 阿矿欢庆日不采矿、不送矿，车上货物先放回矿区库存，再参加聚会。到期配送留待普通日，成功送达后重新计算下一次日期。
- 阿森欢庆日不选择采菇或巡林，下一普通日清晨再决定。
- 普通农务任务在欢庆日停止，植物仍生长，已存货物保留；有效订单获得一天顺延。

## 9. 怎样把状态画成地图

[art/render.js](../js/art/render.js) 的 `render()` 每帧读取当前状态并组合场景。像素树木、房屋、人物与作物主要由 Canvas 图元绘制，生长外观和季节色板通过参数变化呈现。

绘制分为三个阶段：

1. 地表：连续地形、河湖、道路、桥面、田地底色、低矮地被与水纹。
2. 实体：`farmSceneItems()` 在 `collectSceneItems()` 中调用各区域模块。独立建筑、树木、货箱、围栏、岸边植物、居民、动物、休息姿态和广场家具通过 `scenePart()` 或绘制项数组进入共同队列。
3. 飞行物与天气：飞行猫头鹰、飞行麻雀、昆虫等使用飞行层；最后叠加云影、雨雪、昼夜染色和柔和灯光。

连续水底和地表色块由 `groundTilePainter()` 按颜色合并填充，并在当前镜头下对齐到屏幕像素边界，避免逐块抗锯齿造成的网格接缝。草地、各处河湖、湿地底色、村口院落和矿坡底色复用这项绘制辅助；水纹与地面细节随后叠加。原世界矩形、岸线命中和模拟状态不变，完整地图 PNG 仍调用同一绘制流程。

[art/scene-depth.js](../js/art/scene-depth.js) 统一按 **层级 → 接地点纵坐标 → 同深度顺序** 排序。`actorDepth()` 使用角色未受跳跃、俯身、庆典弹跳影响的脚底；角色经过建筑、树木或围栏时，自然从它们后方走到前方。已删除 `workerBehindScenery()` 和 `courierBehindScenery()` 的旧区域矩形判断。

有高度的附着物使用承载物的接地点：停枝猫头鹰在对应树之后，停栖麻雀在水井、屋顶、舞台或木柱之后；彩带使用两根支柱的深度。桥面与桥栏、围栏后侧/侧面/前侧分别登记，菜圃上下排植株也分别登记。休息姿态不再固定最后补画。窗户亮色画在原建筑内，夜间大气层只提供柔和光晕，不重画实体盖住前方角色。

新增实体应同时提供稳定的绘制项标识、接地点及必要的分件。细节、示例和回归范围见 [渲染与遮挡](渲染与遮挡.md)。

绘制函数不推进采收、货运或角色日程，资源结算归行为层处理。这样普通视窗和完整地图导出可以复用同一套 `render()`。

## 10. 视角、点击与提示怎样对齐

世界大小是 **2304 × 1920**，田地网格单位 `T = 32`；普通画布只显示其中一部分。`farm.view.x/y` 表示视窗左上角的世界位置，`zoom` 表示缩放。

```text
浏览器指针位置
  → 按 canvas 的 CSS 尺寸换算画布坐标
  → 扣除世界小于主视窗时的居中留边，并除以缩放
  → 加上 view.x / view.y
  → 得到世界坐标
  → 对象命中 / 区域提示 / 点击动作
```

居中留边由 `worldPadding()` 计算。指针换算入口分别为 `mousePosition()` 和 `screenToWorld()`；小地图则通过 `miniToWorld()` 换算后调用 `centerCamera()`。

普通模式最低缩放为 `.7`；纯享模式最低值取 `min(W / WORLD_W, H / WORLD_H)`，允许完整地图缩到一边刚好贴边，另一边较小时居中补边。`clampCamera()` 限制视角和缩放，`setZoom()` 尽量保持鼠标指向的世界位置不动。

### 10.1 输入分派

[ui/map-input.js](../js/ui/map-input.js) 按顺序判断居民、田地、动物、采集物、鱼点、香草、苗床等目标，再调用对应行为函数。工具 `inspect / plant / water` 影响田地操作；命中顺序也会决定重叠位置上的点击交给谁。拖动后短暂屏蔽点击，避免拖动地图同时误操作。

### 10.2 动态悬停

[ui/inspection.js](../js/ui/inspection.js) 的 `describe(x, y)` 返回文本与目标标识；[ui/hover.js](../js/ui/hover.js) 保存指针的屏幕坐标，每约 100 毫秒重新换算并检查一次。

同一目标仍在鼠标下时，显示最新生长或工作状态。目标移动离开、被采集或失效时清除提示，不自动把旧提示换成脚下草地或新路过的角色；再次移动鼠标才选择新的目标。拖动、窗口失焦和关闭纯享提示也会清理提示。

## 11. 右侧界面如何刷新

总入口是 [ui/dashboard.js](../js/ui/dashboard.js) 的 `updateUI()`。它读取世界与角色状态，更新日期、天气、金币和控制按钮，再分别调用账本、近况、订单、日记、视角、小地图和悬停刷新函数。

自动演变时约每 200 毫秒刷新一次，采集、送货、跨日、按钮操作等事件也可立即刷新。`record()` 会把事件加入 `farm.events`，保留当天全部记录，并调用 `updateUI()`。`nextDay()` 在日期递增后、晨间与欢庆记录产生前清空前一天的日记；统一导入函数只保留存档当天的有效记录，不限制条数。`journal.js` 使用日期和消息内容作为刷新签名，同一天新增消息时保持阅读锚点，跨日时回到顶部；列表仍按四条记录的高度提供内部滚动。

`dailyJournalText()` 只读取当天事件，复制数组后反转原来的最新优先顺序，并使用与界面一致的 `playerJournalText()` 生成日期标题及逐条时间/内容。以发生顺序反转而不是排序钟点，避免农场一天中午夜之后的记录被提前。`copyDailyJournal()` 由用户按钮触发，优先使用 Clipboard API，不可用或被拒绝时用临时只读文本框回退复制，随后删除文本框并恢复焦点；失败显示重试提示。复制期间防止重复操作，不记录新的事件、不修改存档。

右侧近况、村庄发展、居民、订单和日记使用限高滚动；各自刷新函数维护展开状态或滚动位置。村庄发展沿用近况的整体高度上限与 `world-status-scroll` 容器，队列与未来计划不各自嵌套滚动；居民名单移入独立卡片，保留原 ID、动态小像和定位交互。首页 HTML 的实际卡片顺序同时决定视觉顺序与键盘阅读顺序：时间、小地图、账本、近况、居民、村庄发展、订单、旅人与小镇、日记、存档、规则。界面显示是状态的输出，不承担采矿、成熟或居民移动的推进工作。

CSS 按组件拆分，`responsive.css` 最后加载，覆盖窄屏布局；桌面侧栏通过 `sidebar-layout.js` 与左侧地图高度同步，纯享模式另由 `pure-mode.js` 调整画布尺寸和布局。

## 12. 自动保存、导入导出与全图 PNG

### 12.1 浏览器自动保存

[core/storage.js](../js/core/storage.js) 使用 `localStorage`，键为 `moss-valley-farm-v1`，内容结构为：

```js
{ version: 1, state: farm, runtime: captureRuntimeState() }
```

未暂停时约每 4 秒保存一次，跨日、部分收获、送达、暂停切换、缩放和其他明确操作也会保存。普通自动工作并非每一步都立即写缓存，所以刷新通常恢复到最近一次保存，而非保证最后一帧。

缓存按浏览器和站点来源区分；协议、主机或端口改变后可能读不到同一份缓存。若缓存无法解析，当前实现保留原始缓存、显示提示，并暂时阻止自动覆盖；有效导入或重新开始会解除这个状态。

### 12.2 ZIP 与 JSON 共用一份世界格式

[ui/save-transfer.js](../js/ui/save-transfer.js) 导出的正文为：

```js
{
  format: 'moss-valley-farm',
  version: 1,
  archiveVersion: 2,
  exportedAt: '导出时间',
  state: farm,
  runtime: captureRuntimeState()
}
```

默认精简 JSON，并用本地 `fflate` 包装成 ZIP。精简只去掉空白，ZIP 只改变容器，两者都不会减少世界字段。

导入流程：

```text
读取文件 → 根据 ZIP 文件头或扩展名识别容器
→ 解压或读取文本 → JSON.parse()
→ parseFarmSave() 校验世界数据
→ validateRuntimeSnapshot() 校验动态数据
→ replaceFarmState() 应用并保存
```

ZIP 限制为一份 JSON 存档，文件及解压正文上限为 2 MB。校验成功之前不替换当前世界。

[ui/default-save.js](../js/ui/default-save.js) 的“加载 v1.2 默认农场”由玩家主动触发：HTTP 页面读取 `saves/v1.2/` 的原始 ZIP，`file://` 页面从同目录的生成脚本数据还原相同 ZIP。按钮版本、日期和请求地址来自同一份 `DEFAULT_FARM_SAVE` 元数据。两条路径均经 `readFarmArchiveFile()` 和 `importFarmText()` 校验，再提示玩家确认替换；确认后同样调用 `replaceFarmState()`。失败或取消保留当前世界，成功后完整状态立即保存到浏览器。成熟存档的暂停和镜头设置随原完整状态恢复；正常启动仍优先恢复浏览器缓存，不自动加载默认存档，也不改变存档格式版本。原 v1.0 文件与副本仍保留。

`replaceFarmState()` 先替换 `farm`、重建角色与资源的基础状态，然后恢复传入的完整动态快照；再同步欢庆、工具、视角和界面，清理鼠标拖动状态，重置帧计时并保存。主循环继续使用新对象，不另开第二个动画循环。

### 12.3 完整地图图片

[ui/map-export.js](../js/ui/map-export.js) 临时将绘制上下文换成 **2304 × 1920** 的独立画布，把视角设为世界原点、缩放设为 1，调用一次 `render()`，再在 `finally` 中恢复原画布、视角与悬停。

生成的 PNG 包括视窗外的地图、当前人物位置、昼夜和天气。导出没有调用 `updateActors()` 或 `nextDay()`，不推进世界。PNG 是画面记录，继续游玩需要 ZIP / JSON 存档。

## 13. 串起来看：一株香草从成熟到售出

1. `tick()` 增加 `farm.phase`，香草的 `valleyHerbProgress()` 因世界时间增长达到 1。
2. `updateFarmWorkers()` 给阿栀分配 `herb` 任务，她沿途走到目标旁。
3. 到达后累计 `action`，完成任务时调用 `collectValleyHerb()`。
4. 该函数记录新的采收与再生时间，把一份香草加入 `farm.depots.valley`，更新计数、日记和保存。
5. 本帧及后续 `render()` 显示采后的植株形态；悬停重新读取生长文字。
6. 阿运返程出发时若香草箱已有库存，就将其列入 `plannedDepots`。
7. 到箱时转移全部现货到 `courier.cargo`；到集市时结算金币，检查建设，再更新界面。
8. 中途导出时，香草再生时间、货箱或货车里的库存、阿栀与阿运的行动阶段都被保存。

这个流程体现了当前代码的分工：**时间推进 → 行为决策 → 状态变化 → 界面与画面读取 → 保存恢复**。

| 货运、订单、建设 | `life/logistics.js`、`core/economy.js` | 规划时点、现货转移、支出和解锁调用 |
| 欢庆活动 | `festival-life.js`、`festival-activities.js` | `festival-budget.js`、居民自身入口与返家 |
| 道路或建筑位置 | `core/world-layout.js` | 所有相关路径、命中、小地图和遮挡 |
| 前后绘制关系 | `art/scene-depth.js`、`art/render.js` | 接地点、附着关系、分件与对应区域绘制函数 |
| 提示与侧栏状态 | `ui/inspection.js`、`ui/world-status.js` | 角色命中、动态刷新和滚动保持 |
| 新增保存字段 | `core/state.js` 或角色创建函数 | `storage.js`、`runtime-snapshot.js`、`world-session.js` |

新增持续变化的数据，需要同时明确它属于世界数据还是运行数据、由谁更新、如何校验和恢复。新增视觉效果，需要先选择合适的时间来源，避免暂停时角色继续移动，或加速时粒子突然过快。

复杂行为修改可运行 `node kits/farm/tests/smoke.cjs`；脚本语法可用 `node --check`。简单文档和样式修改按实际风险做针对性检查即可。测试读取首页脚本清单，修改加载顺序时不需要另维护一份测试脚本列表。

## 城镇扩展的数据流

`town-layout.js`、`town-config.js` 和 `town-state.js` 在初次读取缓存前加载。已有 v1.0 存档缺少城镇字段时，`parseFarmSave()` 补充 `makeTownState(state.day)`，随后校验；既有金币、货箱、作物和角色运行状态继续保留。阿棠、鸟蝶、库存和预算存于 `farm.town`，直接随完整 `state` 导出。阿宁的茶会进度在 `town.childVisit`，实际位置仍在 `runtime.villageWalker`。

每帧 `updateActors()` 首先准备本日城镇状态和当前季节预算，再更新阿棠；阿宁日常更新会检查茶会行程，末尾更新城镇鸟蝶。它们都沿用主时钟；暂停时不做决策、不扣款、不移动。`updateUI()` 只显示商品与预算，不决定来访或购买。购买按钮调用 `townBuy()`，先检查营业、库存、经营储备和自动预算，再扣钱、记录见闻、刷新并保存。每趟商品和随机种子已经保存，导入恢复不会重新抽样。

公共委托由 `town-projects.js` 管理。`townCommission()` 一次扣款并创建 `town.construction`，记录项目、目标阶段、费用、开始时间与进度。阿棠在 `town-traveller.js` 中进入前往工地、工作、返程状态；没有完工前不会离访，夜间与欢庆日先回家或赴会。完工写入 `town.improvements[id]`，保存每阶段的日期，不重复收费。每趟自动委托标记 `traveller.commissioned` 同样保存，刷新不会再接一项。

`town.plantings` 保存购买花种的种植日期，设施的 `improvements[id].stages` 保存每阶段完工日期。绘制根据当前世界时间计算约 1.2 天的连续长势，不修改状态；暂停时真实动画时钟继续，但植物的世界时间不变。逐排记录保证升级不重置已长大的花。

`updateTownCare()` 在城镇准备之后、阿棠更新之前读取天气，按每项 `agedAt` 每日累计一次 `wear`；未建设地点只更新结算日期。养护任务的 `construction.kind` 为 `care`，新建为 `build`。养护复用施工路线和停止时刻，完成只清零需求、更新 `lastCare` 与 `maintenanceCount`，不升级或重种。`town-development.js` 的只读 `townDevelopmentPlan()` 先列出预算可负担的候选：建设按阶段数、最近建设日期、费用排序，养护按需求排序。通常先考虑 0.85 以上需求的养护；`autoCareStreak` 达到二且有可建设候选时，先留一次建设机会，否则仍可养护。成功自动养护时标记累积到二，成功自动建设后清零；手动安排不影响它。`townChooseCommission()` 只在未暂停、普通营业日上午 0.20—0.30 时接单，每趟仍限一次。侧栏/地图面板调用同一只读说明，反复刷新不抽样、不扣钱、不改变顺序。

生态更新之后调用 `updateTownGardenLife()`。`gardenChoice` 记录当天蜗牛与刺猬选择，包括未出现的结果；`critters` 保存动物、目标、停留时间、缩壳时间与是否已观察。蜗牛白天、刺猬秋日黄昏沿花园南侧草地活动，离开时走回叶堆，不瞬移去建筑。冬日知更鸟仍由鸟食模块管理，类型 `variant=2`，不进入翠鸟 `variant=1` 的潜水行为。`noticeTownAnimal()` 只在首次观察时增加 `observations`，重复点击不会重复计数。

所有人物本帧移动后，`updateTownGreetings()` 检查阿棠附近可见的居民。`traveller.greetings` 保存日期、已问候名单与冷却，不修改居民的任务或路线，仅设置双方 `waveUntil`。`townBeginVisit()` 选定本趟 `storyIndex`，`townReadStory()` 检查营业和 `storyHeard` 后记录一次；茶会读取同一个故事，使用原来的 `chatDay` 防止每日重复喝茶。通用问候不写 `chatDay`，因此不会阻止阿宁本来计划的茶会。

茶亭任务出发时 `townPrepareTeaParcel()` 将驿屋库存转入 `traveller.carriedTea`，不再次收费。实际进入茶亭工作状态后 `townDeliverTeaParcel()` 转入 `town.pavilion.tea`；返屋的未交付货物由 `townReturnTeaParcel()` 退回，满库存的余包仍在演员身上。阿矿更新后，`updateTownPavilionTea()` 在 `teaRest` 状态检查 `pavilion.minerTrip !== miner.deliveryDay`，有库存才消费一杯，保存这趟的出发日、茶亭招待和总招待数。绘制读取库存，使用共享茶箱坐标并登记接地点。

驿屋、货车、居民和巢箱通过 `scenePart()` 加入普通接地点队列，停栖鸟继承浅盘或巢箱的深度，飞鸟和蝴蝶进入空中层。地图货架属于地图面板内部，因此原生全屏中仍可购买。道路、小地图和完整图片导出都使用 2304 × 1920 的世界尺寸。


所有角色和生态更新后调用 `updateTownLanterns(dt)`。`town.lanternEvent` 保存当天选择、是否举办、费用和每盏的年龄/等待，`lanternCount` 与 `spending.lanterns` 保存累计；`townLaunchLanterns()` 先检查时段、天气、储备与当天举办标记，实际结算后才创建纸灯。绘制和提示共用 `townLanternPosition()`，不修改年龄；起飞前按落地点排序，起飞后进入空中层。地图面板由舞台点击打开，付费只由明确的举办按钮或受预算限制的自动决策执行。


纸灯更新之后调用 `updateTownFireflies(dt)`；`town.fireflyChoice` 保存当天两个栖息地的选择、出现和观察标记。`town.fireflies` 保存实际位置、目标、停留、年龄与渐显/渐隐值。生态移动仅用世界 dt，`townFireflyGlow()` 只用真实显示时钟闪光，因此暂停不会偷偷移动。点击命中当前位置并调用群体观察，整夜累计最多一次；两处栖息地、绘制、提示和小地图复用 `TOWN_LAYOUT.fireflyHabitats`。


收藏由 `TOWN_GOODS` 声明，数量保存于原来的 `town.inventory`；复用 `townBuy()` 的一次购买、真实支出与保存。`townBeginVisit()` 先过滤满库存商品，再优先当前财富阶段；空库存目录也是有效来访，故事、施工与生命周期继续。`town-curio-art.js` 读取数量，将收藏附着在共享坐标的柜体里，接地点为柜底；命中与小地图复用同一柜体范围。收藏卡片只改变视角，不重设地区或居民状态。


阿棠更新之后，`updateTownDog(dt)` 比较 `town.dog.visit` 与 `town.visits`，首次看到新一趟来访时选择是否同行。小狗使用自己保存的路线和索引，复用道路步进但有独立目标，不绑定商人的瞬时位置。天气/欢庆/傍晚促使它沿原路或驿屋侧道返屋；离访优先，直到出口才设为不可见。绘制只读行为和接地点，尾巴使用真实显示时钟；每日招呼仅更新挥尾反馈和一条记录。

阿棠营业且无委托时，由 `townChooseMerchantRest()` 保存当天午后选择。选中则进入 `walk/tea`，真实抵达后 `townBeginMerchantRest()` 转为 `rest`、扣一杯已有花茶并增加 `town.selfTea`。`updateTownMerchantRest()` 用世界 dt 累计等待，结束后按路线回柜；夜归和欢庆优先。演员的 `restDay`、`drinking`、`wait` 与路线都在 `town.traveller`，不额外放入 runtime。椅背、坐着的人和椅脚分别登记深度，绘制不消费库存。


所有居民本帧移动之后调用 `updateTownDogGreetings()`，复用 `townNearbyResidents()` 的可见性列表，选择 64 像素内最近的邻居。只设置双方的原地回应与 `dog.friendDay/friendName`，不更改任务、路线、位置或等待。每天最多一次，暂停、欢庆和返屋/离访不触发；玩家的 `greetedDay` 独立保存。侧栏读取当天名字，不参与行为决策。


### 邻里午后茶会的角色协作

`town-tea-party.js` 保存 `town.teaParty` 的邀请、固定价格、客人路线/索引、等待、付款标记和返家目的。`updateActors()` 在本日准备与养护后、阿棠移动前调用 `updateTownTeaParty()`，只在两人真实到座后使用 `townSpend(cost, 'gatherings', automatic)` 一次付费、取两杯已有库存，再写入 `teaParties`、招待和自用累计。未选中自动邀请的结果同样立即保存。

阿棠仍由 `town-traveller.js` 管理自己的路线，等客时保持座位；阿葵在 `updateOrderKeeper()` 的共享欢庆处理之后、普通菜圃工作之前检查 `updateTownTeaPartyGuest()`，只临时接管移动，不清空 `gardenWork`。路线经过共享北街坐标 `TOWN_LAYOUT.northLaneY`，雨天只反向走已到过的路点，夜间返回自己家；欢庆优先。阿葵的位置和步态仍在 `runtime.orderKeeper`，茶会状态在 `farm.town`，完整恢复时两者必须一起使用。

侧栏与地图货架复用 `town-tea-party-dashboard.js`，显示邀请条件和本次固定费用；不在 UI 刷新时抽选择或扣款。`town-tea-party-art.js` 只画季节点心，附着原茶桌；人物使用共享坐姿画法，在原角色绘制队列中排序，没有另画一个副本。小地图与完整 PNG 沿用两位演员的实际位置。


### 购买的猫玩具如何进入原猫咪日程

`town-cat-play.js` 用 `farm.town.catPlay` 保存每日兴趣、结束标记、当前猫/球、拨球次数、等待、球的位置和目标、累计完成次数。`townPrepareCatToys()` 在第一次持有玩具或每日更新时建立球和一次保存的兴趣；日日期与猫编号的 hash 不消耗商人的随机序列。暂停不自动准备或推进，明确点击球可以准备并排一个走近目标。

`updatePlazaLife()` 先推进球，再执行原来的两只猫与麻雀。`choosePlazaCatWalk()` 优先提供有兴趣的球位置，`plazaPetPath()` 使用原避障网格并在最后追加清楚的球落点；`updateTownCatPlay()` 只有猫已经进入共享矩形空地后才接管追球。目标和直线段都在这块无障碍空地内，拨三次后交回原来的洗脸/散步行为。雨雪、夜晚和欢庆释放占用，原猫屋返程仍由 `plaza-life.js` 执行。

`town-cat-play-art.js` 只读球状态，逐颗加入绘制队列；原 `drawPlazaCat()` 扩充拨爪动作。球的命中优先保留猫与村民本人的提示；地图点击明确调用 `inviteTownCatPlay()`，侧栏显示累计次数。`runtime-snapshot.js` 允许猫的 `play` 行为，仍由其捕获实际猫位置；城镇导入校验检查球的数量、范围、路线目标和占用。没有新增演员副本、产物、货箱或收费。


## 东岸新增生活的调度

`updateActors(dt)` 在城镇规划与设施养护之后更新花盆湿度，再更新邻里茶会与阿棠，随后更新豆豆和小驴。花盆以保存的世界时间差平滑累积湿度；阿棠普通调度给已有施工优先权，再在合适上午尝试浇水。浇水子状态控制实际逐盆路程和停留，结束后恢复普通回柜/归家路线。雨雪、欢庆和暂停仍由同一世界时钟与天气体系决定。

小驴按已完工的驴驿阶段创建，先在棚内，再真实走到草场。每次随机目标与动作保存后才继续行走，不在渲染时选择目标。天气或夜间触发经围栏开口的回棚路线；半途出棚会反向走完已走的通道。玩家问候与工地遇见阿棠只做免费局部回应和每日去重，不增加货运或产量。

`farmSceneItems()` 收集山脊、棚屋、围栏各段、水槽和可见小驴；建筑与动物均使用接地点排序。矿坡地表只绘制到自身东界并渐弱收边，东侧保持原有连续草地。`WORLD_W=2560` 同时用于摄像机、最低全屏缩放、小地图坐标与全图 PNG 的尺寸。茶院搬迁只更新共享坐标和线路，已有进行中的旧座椅访问会沿原路径结束，付款与茶库存不再次结算。


## 阿宁探访小驴的调度

`updateTownDonkeys(dt)` 先按已保存的日程更新动物，之后 `updateVillageWalker(dt)` 处理阿宁。欢庆优先取消探访并沿共同聚会安排行走；普通日已有探访先续行，没有探访时先尝试既有茶院访问，再检查小驴探访机会，最后使用原散步/夜归逻辑。同一阿宁不会同时拥有两条活动路线。

每日第一次符合晴暖清晨条件时保存抽选；出发保存一条共用地图路标的路线及报价，扣款不在此处发生。路线阶段依次为 `out → wait → feed → return → home`；动物在北门出棚后才接受东门等候目标。`wait` 只有人物与动物实际到门边、储备/预算再次检查通过才结算一次，`paid` 和独立支出立即保存。`feed` 只累积 3.5 秒世界等待，随后按已经走过的路标反向回家；路过自家门口时截断散步起点，返家速度仍为原值。

变天、太晚、小驴归棚或新工地中止未结束的探访，未结算的不收费。`home` 隐藏人物并保留当天居家，次日清掉该阶段后从真实家门出发。暂停阻止此调度推进，但绘制继续原地动作。当日未选中也保存，缓存、JSON、ZIP 与刷新均保留选择和进度；新计数及子状态缺失时补为未发生，不改变已发布默认农场内容。


## 溪畔雨水与浴鸟的演变

`updateActors()` 在普通鸟类生态后调用 `updateTownBirdBath(dt)`。未添巢箱时保持默认未启用；启用时存入初始水量，之后使用 `farm.day + farm.phase` 和已保存时间戳的差值累积雨水/蒸发，沿 `weatherVisual()` 的雨量和季节权重连续变化，暂停不推进。

每日首次符合晴暖白天与水量条件时保存一次随机决定；选中才创建一只访客，从共享溪边点真实飞向浅盘。`arrive → perch → bathe → dry → leave` 各阶段只在实际到位或等待完成后推进，来访在抵达时计数，洗澡每完成一回消耗少量盘水。变天、寒冷、暮色或缺水切换到离开目标，走完航程才清掉鸟体；每日选择仍保留，不重新生成。野生访客不参加村民停工调度，欢庆日仍按天气生活。

水位/每日选择与鸟体由城镇保存，观察沿已有 `noticeTownAnimal()` 去重并计入白鹡鸰分类。浅盘绘制只读取水量；落水鸟、水滴与盘的承载深度一致，飞行使用空中层，缓存、JSON、ZIP、小地图和全图 PNG 都采用同一位置。原有翠鸟与鸟食生态保持自己的状态与时钟。


## 冬夜暖炉如何衔接商人日程

木柴由 `townBeginVisit()` 按冬季权重筛入本趟货架，实际价格和售罄状态仍是来访快照。`townBuy()` 在购买时扣款、增加四份库存，自动购买沿用公共预算；`townGoodsUseful()` 在暖季不申请自动补柴。

统一行为调度先更新阿棠的位置/模式，再调用 `updateTownHearth(dt)`。暖炉只读取真实家门距离、普通在家或欢庆返家状态，在冷夜首次符合条件时保存 `hearth.day/chosen`。选中才减一份木柴并增加 `nights`；亮度独立连续推进，失去条件或跨日先关闭活动再渐暗。`farm.paused` 在函数入口冻结这些变化，绘制用 `now` 保留火苗/烟的轻微运动。

`farm.town.hearth` 与 `inventory.firewood` 一起保存在完整世界状态中，导入只为缺少新字段的旧城镇补默认值；火炉不会另存角色或复制家门坐标。绘制回调把火苗附在原驿屋窗口，柴堆使用自身接地点，烟才进入空中层。界面读取同一状态，缓存、JSON、ZIP 和完整 PNG 共用同一套流程。


## 蝴蝶如何找到实际花头

`townNectarFlower(siteIndex, seedIndex)` 从共享八个花簇、已有种植时间与连续长势算出花头坐标、高度、开花程度和承载深度。新花绘制直接使用该结果；`townButterflyFlowers()` 只返回长势达到 75% 的花头，补种的嫩株与成熟株分别判断。

统一调度通过 `updateTownButterflies(dt)` 推进蝴蝶，脱离普通鸟类更新。晴暖白天有可落花目标、当天尚未来过且没有旧群体在返程时，创建并保存两到四只访客。`townButterflyChoose()` 从未被其他蝴蝶占用、不同于上一花簇的花头中随机选择目标，蝴蝶真实移动到目标再进入 `sip`。完整等待结束才增加 `nectar.sips` 和个体 `sips`，三回后或环境不适合时转入 `leave`，实际到达保存的家方向才移除。未完成等待不累计，转晴不重来。

随机种子、`nectar.day/sips`、蝴蝶位置/目标/家方向/动作/等待/当前花头/上一花头/个体回数/是否观察与分类累计全部在 `farm.town` 中保存；不复制到旧居民 runtime。绘制只读取状态，停栖跟随花簇，飞行使用空中层，暂停时用视觉时间保留翅膀动作。侧栏、小地图、悬停和全图导出读取同一对象。
